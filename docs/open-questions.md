# Open questions

Things still unknown, and the assumptions the service relies on until they're answered. Each
question says who can answer it, what the service assumes meanwhile, and what breaks if
the assumption is wrong.. Bugs:
[known-issues.md](known-issues.md). The README's *model risk* section is built from this.

**Who can answer**
- **MarketPay**: only they know; ask them.
- **Experiment**: a test on the staging terminal can find out.
- **Decision**: for the design to make; record the choice and the trade-off.

---

## For MarketPay

| Question | Assumed meanwhile | If wrong |
|---|---|---|
| What's the **longest a transaction can stay unrecorded**? Is the ~120 s card timeout fixed or configurable? | 180 s (`TERMINAL_MAX_TRANSACTION_SECONDS`). After that, "no record of this payment" = it never ran. | A payment the service marked `failed` / `never_recorded` could still complete → **a lost payment**. |
| When does `last-transaction` report **`IN_PROGRESS`**? Staging never showed it: a running transaction is never reported. | It doesn't; a running transaction looks like "not the payment's own". | If it did, the service could decide faster. It's no risk, only lost speed. |
| What does abort **`409`** really mean? Can a transaction be aborted after its request got a `202`? On staging it can't. | 409 = "nothing I can abort", with no information either way. Only a 204 stops anything. | If 409 could also mean "stopped", the service would leave `unknown` payments longer than needed. It's no risk. |
| After a **`204`**, is the transaction guaranteed not to complete? | Yes: 204 + no record of this payment → `failed` / `aborted`. | A charge could stand behind a `failed` record → **a lost payment**. |
| Is **`ecrTransactionId` an idempotency key**? What happens if a completed one is sent again: deduplicated, rejected, or **charged again**? | Unknown, so the service never re-sends anything that may have arrived. | Re-sending must stay limited to requests that certainly never left the service (connect-phase failures). |
| Is **`cancellationResult`** ever filled in `last-transaction`? Staging shows a reversal as a normal `transactionResult`. | Both shapes can occur; recognise both. | If only one shape existed, part of the code would be dead, but harmless. |
| Is `cancel-transaction` always a **card-present refund** on this terminal type? Is it the same as `process-transaction` with `transactionType: REFUND`? | Yes, card-present; the REFUND transaction behaves the same way (covered by tests; staging never produced it). | MarketPay may treat the service's "approved despite abort → REFUND" path differently from what the code assumes. |
| Is a **terminal-side cancel** reported with a distinct code? On staging it looks exactly like "no card in time". | No; NOK without a code = stopped before the bank. | Only a less precise `state_reason`. |
| How long can a request be **delayed in transit** and still start a transaction? | Short enough that the service's checks after the deadline catch it ([flows §5](flows.md#5-re-checking-inferred-outcomes)). | A late request could charge after the service reported `failed` → **a lost payment**, until the re-check corrects the record. |
| Does staging approve through a **simulated host**? The `authorizationCode` is always `213462`. | Yes; no money moved in the observed test runs. | Unexpected charges; check processor/account records. |
| How does the API behave when the terminal goes **offline mid-transaction**? | Lookups fail and aborts are refused; the payment stays `unknown` and the service retries later. | Unknown. |
| What does **`PARTIAL`** look like in practice, and does `cancel-transaction` reverse a partial charge **in full**? Does it need the approved amount rather than the original one? | The service sends the original amount and trusts `status OK` of the reversal. | A partial charge could remain standing behind `declined`, or the reversal could be refused (then it's flagged for a person). |
| Is the **one `last-transaction` per terminal at a time** limit intended? Are other endpoints also affected, e.g. `last-transaction` while a `process-transaction` for that terminal is open? | Only `last-transaction` overlaps fail; the client serialises them per terminal. | Other overlapping calls could fail too; they'd show up as transient errors and be retried. |
| Which **4xx** can `process-transaction` return besides the documented `400`/`404`? In particular, what does MarketPay answer when a transaction is already running on the terminal (e.g. a duplicate of the payment's own)? | Only `400`/`404` prove nothing started; any other 4xx is treated like a lost answer. | If a busy terminal answered `404`, the service would call it `failed` with a copy running. The confirming look would only catch a copy that had already finished. |
| Which **4xx** can `cancel-transaction` return, and can any of them mean the reversal may still run (e.g. a `409` while the terminal is busy)? | Any 4xx is "not done": the charge stands, the terminal is freed, and a later cancel may retry. | A reversal that did run would be recorded as not done: the record would say "charged" while the money is back. The next cancel's re-check would not catch it (it isn't an inferred outcome). |
| Why is `finalTransactionParams.transactionType` never echoed, though the spec marks it required? Does production echo it? | It's never there; the service never relies on it (purchase vs reversal by `terminalTransactionId` + baseline; refunds have their own reference). | Nothing breaks; if production did echo it, it would be a simpler, stronger way to tell a reversal from a purchase. |
| **How can the service tell a notification really came from MarketPay?** The guide says the call is not authenticated; only an unguessable URL protects it. Do notifications come from **fixed IP ranges** the service could allowlist? Is there a **signature header**, or mTLS towards the service's endpoint? | Only the service's signed URL (an HMAC of payment id and operation, never logged). Anyone who learns one URL could post a fake result for that one operation. | A forged `COMPLETED` could record a phantom approval or a false decline (and the waiter runs the card again). **Before trusting notifications in production, add at least an IP allowlist**, and verify any signature MarketPay offers. |
| The **final** notification is sent after a `202` and after a `201`, unlike the spec. Is it also sent when the service's request died (connection reset, a service crash)? Are reversals (`cancel-transaction`) notified, and in what shape? Why were no progress notifications sent? | Unknown; see the notifications experiment below. | Decides whether the webhook can settle anything that polling doesn't. |
| What does **`409` from `process-transaction`** mean (seen once)? Terminal busy with something the service can't see, a duplicate `ecrTransactionId`, or rate limiting? | Like any undocumented 4xx: proves nothing, watch → abort → confirm. | If it meant "a transaction of yours is already running", the abort would stop it; if it meant "already done", the confirming look finds it. Either way no wrong state, only a failed payment the waiter retries. |

Hard to set up; maybe by forcing the path in a debug build. |

## Decisions (made, recorded here with the trade-off)

| Decision | Trade-off |
|---|---|
| **The truth wins over the deadline.** If the service's abort is too late and the payment completes, report **`approved`**. There's no automatic refund. | The waiter may get `unknown` at the deadline instead of a clean `failed`. |
| **`PARTIAL`**: reverse it right away, within the payment request (the customer is still at the terminal for the reversal's tap), then report **`declined`** with `reversed: true`, `declineReason` = MarketPay's code verbatim, and `state_reason: partial_approval_reversed`. It is always a **reversal by `terminalTransactionId`, never a REFUND**, because a refund names an amount and MarketPay never tells the service how much was approved. If it can't be reversed (refused, not sent, no time left, no transaction id, or a crash before the reversal was claimed), the payment becomes `unknown` with `partial_not_reversed`, the **terminal is freed**, and a person must settle the charge. A POS cancel then answers `409 needs_attention`. | The customer pays again with another card, although part was approved. A partial charge that couldn't be reversed needs manual follow-up. Recovery never starts the reversal on its own, since the customer may be gone. |
| **A reference is one attempt.** Retrying a declined or failed order needs a new reference. Repeating a reference returns the existing payment only if it's **the same order** (terminal, amount, currency); otherwise it's `409 idempotency_mismatch`. `deadlineSeconds` may differ, because it describes the request, not the order. | The POS must generate `order-123-2` etc. A POS bug that reuses an order id for a different amount gets an error instead of someone else's payment. |
| **NOK without an acquirer code → `failed`**, not `declined`. | If production ever sends a real bank decline without a code, the waiter retries the same card. |
| **Reconcile never starts a new card transaction** (a refund that was due is released as `approved` / `refund_due`). | The charge stands until the POS cancels again. |
| **One process per `INSTANCE_ID`** (one gunicorn worker). | Throughput comes from threads, not processes. |
| **`status` decides the outcome, not `responseCode`.** A result with `responseCode "000"` (which the spec calls approved) but `status NOK` counts as **`declined`**, with `declineReason "000"`. The contradiction is logged at **error** level (`marketpay_result_inconsistent`, once per record) and kept in the payment's `state_detail`. | The service never reports an approval MarketPay's own status denies, so no phantom charge. If `status` were the wrong field and `responseCode` right, a charge could stand behind `declined`. The error log is there so a human notices and asks MarketPay. The opposite case, **`OK` with a code other than `000`** (or none), is flagged the same way; it stays `approved`. Logs are detailed enough to take up with MarketPay: status, code, authorization code, the echoed amount, currency and type, and card capture (no card numbers). |
| **When Firestore fails**: retry transient errors (contention, outage, timeouts) with backoff, from 0.1 s doubling to 1 s. **Before anything was sent to MarketPay**: give up after 5 s with `503 store_unavailable` (nothing was charged; retrying with the same reference is safe). **After MarketPay answered**: keep retrying until the request's deadline, then **return MarketPay's outcome anyway** and log an error. The stored record lags behind but still holds the terminal lock, and converges through a later recheck or reconcile. Write-ahead notes (e.g. "abort requested") are best effort. A timed-out write may have landed, so claims recognise their own earlier write. | The POS never gets a 500 for a charge that happened. The price: for a while, the stored record (and so `GET`) can lag behind what the POS was told. |
| **`GET /payments` needs no Firestore composite index.** Firestore only sorts by `createdAt` and applies the date range (the automatic index covers that). State and terminal are filtered in the service while scanning, `reference` is a direct lookup (the id is derived from it), and one request examines at most 2,000 documents (then `nextCursor` resumes the scan). The listing returns stored state only. | Anyone can run the service against their own Firestore project with no index deploy step, and a missing index can't fail requests. The price: a sparse filter over a very long history pages through many short pages; add composite indexes if that ever matters. |
| **Outcomes the service only inferred are re-checked once.** These are `failed` / `aborted` with no record of this payment, `failed` / `never_recorded`, and `approved` / `undo_not_recorded`. When such a payment settles, its terminal is flagged. The **next payment** on that terminal looks at `last-transaction` once before sending anything, then clears the flag, because its own transaction will overwrite the evidence. **Reconcile** also checks flagged terminals, but keeps the flag if it finds nothing (a late request may still land). A late charge → the record is corrected to `approved` / `late_charge_found`. A late reversal → `cancelled` / `late_reversal_found`. An error is logged either way. **Never reversed automatically.** | Records always match what MarketPay holds, so no `failed` record ever stands for a real charge. The charge itself needs a person to refund it, because an automatic reversal would put "Refund, present card" in front of the next customer. It costs one lookup only on a flagged terminal. A late request that is still *running* at the check isn't visible. |
| **Reads never ask MarketPay.** `GET /payments/{id}` and `GET /payments` return the stored record as is. Unresolved payments converge through explicit actions only: `POST /reconcile`, a POS retry of the same order, a cancel, or the next payment on the terminal. | One source of truth for every reader, and a `GET` can never change what another reader just saw: eventual consistency that is predictable. The price: an unresolved payment stays `unknown` in reads until one of those actions runs. |
| **A payment is one `PURCHASE`, not a `PRE_AUTHORISATION` + `PRE_AUTHORISATION_COMPLETION`.** (1) The waiter needs a *definitive* approved/declined within seconds; a pre-auth only reserves the money, so the order isn't paid until a second transaction completes it. (2) The bill is known when the card is presented; pre-auth exists for amounts known only later (hotels, car rental, fuel, bar tabs). Tips go into the same purchase (`amountTip`, entered before the tap), not via the US-style "authorise, then add the tip". (3) It doubles the risk it seems to reduce: the completion is a second terminal transaction that can lose its reply, be refused or crash, and a lost completion leaves money *held but never captured*. The terminal would also have to stay locked between the two steps, or the pre-auth's evidence is overwritten. (4) Its apparent benefit is weak: an abandoned pre-auth isn't a second *charge*, but the customer still sees a second hold for days. (5) The brief's invariants ("at most one standing charge", "reverse a completed payment") and its checks against `last-transaction` are about purchases. | Amounts can't change after the tap (no tip-after-authorisation, no open tabs). If a customer ever needs that, it's a new flow with its own recovery design, not a variant of this one. |

## Decided for one terminal, to revisit at scale

| Decision | Why, and the path at scale |
|---|---|
| **Reconcile handles open payments one by one.** | A terminal has at most one open payment, so with one terminal there is nothing to run in parallel. With many terminals, reconcile each terminal in parallel: their payments are independent. |
